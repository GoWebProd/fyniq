# AGENTS.md — форк fyniq

Это форк [TNT-Likely/BeeCount](https://github.com/TNT-Likely/BeeCount) (Flutter-приложение для учёта финансов).
Файл описывает правила работы с ветками в форке. Правила кода, сборки и стиля коммитов берутся из апстрима:
`docs/contributing/CONTRIBUTING_EN.md`.

## Remotes

| remote     | URL                                          | назначение                                            |
|------------|----------------------------------------------|-------------------------------------------------------|
| `origin`   | https://github.com/GoWebProd/fyniq.git       | наш форк                                              |
| `upstream` | https://github.com/TNT-Likely/BeeCount.git   | исходный проект, только fetch (push отключён намеренно) |

Если `upstream` не настроен:

```bash
git remote add upstream https://github.com/TNT-Likely/BeeCount.git
git remote set-url --push upstream DISABLED
```

## Ветки

- **`master`** — базовая ветка форка. Сюда попадает всё, что есть в нашей сборке: апстрим, наши фичи и
  файлы, нужные только форку (этот AGENTS.md, брендинг и т. п.). Все PR внутри форка направляются в `master`.
- **`main`** — чистое зеркало `upstream/main`. **Коммитить в `main` нельзя**, она обновляется только fast-forward
  из апстрима. От неё ответвляются фичи, которые мы можем отдать в апстрим.
- **Ветки фич** — по одной на фичу, с именами в конвенции апстрима: `feature/…`, `fix/…`, `refactor/…`, `docs/…`.

### От какой ветки начинать фичу

| фича                                                         | база     | PR                                          |
|--------------------------------------------------------------|----------|---------------------------------------------|
| потенциально полезна апстриму (переводы, баги, общие улучшения) | `main`   | в `master` форка; при желании тот же бранч — PR в апстрим |
| нужна только форку (брендинг, наша инфраструктура)             | `master` | в `master` форка                            |

Почему фичи для апстрима начинаются от `main`, а не от `master`: иначе в PR в апстрим попадут коммиты,
которые есть только у форка. По той же причине такие ветки не должны зависеть от изменений, существующих
только в форке. Если без этого не обойтись, фича считается fork-only.

Правила для upstream-совместимых веток:
- коммиты по конвенции апстрима (Conventional Commits: `feat(i18n): …`, `fix(…): …`);
- не трогать файлы, которые есть только в форке;
- перед PR в апстрим выполнить rebase на свежий `upstream/main`.

## Синхронизация с апстримом

```bash
git fetch upstream
git checkout main && git merge --ff-only upstream/main && git push origin main
git checkout master && git merge main          # merge, не rebase: master опубликован
git push origin master
```

Если `--ff-only` не проходит, значит в `main` кто-то закоммитил. Перенесите эти коммиты в отдельную ветку
и верните `main` в состояние `upstream/main`.

Открытые upstream-совместимые ветки обновляются через `git rebase main`, пока их не смержили в `master`.

## Служебные файлы форка

В `.gitignore` апстрима есть `AGENTS.md` и `CLAUDE.md`. Мы не правим `.gitignore`, чтобы не получать конфликты
при синхронизации. Такие файлы добавляем в индекс через `git add -f` один раз, дальше git отслеживает их как обычно.
